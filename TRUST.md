## ISA model and decoder

Existing ISA: `third_party/s2n-bignum/x86/proofs/x86.ml`; decoder: `x86/proofs/decode.ml`; relational foundation: `common/relational.ml`; safety foundation: `common/safety.ml`, all at the pinned revision. The `x86` relation fetches and decodes bytes from modeled memory, increments RIP by the decoded length, then applies `x86_execute`. Proofs must cover the actual encodings and operands rather than supported mnemonic names alone.

The pinned `x86state` represents RIP, general registers, vector registers, mask registers, rflags, byte memory and events. Memory is a total `int64 -> byte` function. There are no modeled allocation or page-permission faults. Therefore a functional theorem or final-state memory frame does not establish intermediate access safety. The separate safety theorem must cover all complete load/store widths, incoming RET-slot read, transient writes, code fetches, and real permission/canonical/nonwrap conditions.

`memaccess_inbounds` checks load/store events using modular range containment. It does not itself establish nonwrapping mathematical intervals, canonical addresses, permissions, code fetches or stack discipline. `events` includes loads, stores and jumps; no instruction-fetch event is generated by `x86`. An instruction/control/fetch trace extension requires checked correspondence to the original transitions; it may not become a second unconnected interpreter.

The `ensures` relation uses universal successor eventuality, including a rule for an already satisfied postcondition. This handles ISA nondeterminism but permits zero transitions unless the target boundary prevents that case. An accepted callable theorem must reach a decoded actual RET transition, restore RSP to sp+8, and exclude a zero-step return. A trace/safety assertion proved only at one convenient final state does not cover every execution.

System V floating-point/control-state preservation, privilege/canonical-state machinery, CET enforcement and OS register enabling are not represented completely. Their model coverage and environment correspondence must be explicit; missing representation is not permission to mark all ABI obligations PASS. No source resemblance substitutes for an instruction/effect argument.

Independent extraction tools should agree on each frozen region and relevant immutable data; this reduces common errors and is not formal verification of either parser. ## Automation and external tools

Disassembly, ELF readers, compilers for new callers, source/header/debug lookup, emulators, native tests, page guards, hashing, clocks and resource meters provide discovery or diagnostic evidence. They cannot discharge universal target theorems. Header/assembly interface checks and symbol resolution observations help identify the ABI/binding but are not checked call composition. Unverified lifting or static call-graph discovery cannot establish ISA equivalence or exhaustive reachable control flow.

Proof tactics may search and fail freely. Their outputs must enter through the logical kernel. Acceptance orchestration is separate from kernel soundness and can falsely report success unless it checks live theorem objects, expected statements/assumptions, dependency closure and artifact bindings. Negative controls exercise those checks; they are not proofs of the acceptance driver's general correctness.

Explicit conditions: 64-bit little-endian user mode; declared CPU instruction support and OS vector state; disabled alignment checking and declared CET condition; canonical48 accessible ordinary memory; stable required pages and immutable code; sequential nonconcurrent execution; correct post-initialization placements/bindings; architectural instruction semantics correspondence; transparent OS execution under the admitted boundary. ## Current accepted scope and enforcement

The restricted OpenSSL package checks three actual-return theorems for n=0 or n=16 and three separate event-range lemmas. The original decoder is retained pristine; the versioned REP_RET_DECODER_V1 overlay is mounted only for affected OpenSSL checks. The glibc selector subclaim uses the original model without that overlay. All other universal contracts remain incomplete.

The current checker reconstructs proofs in a new offline process from read-only pinned sources. It compares each live HOL theorem's empty hypothesis set and conclusion against the independent frozen term, then checks that no axiom was added to the foundation's initial set. Generated JSON dependency names describe the proof recipe; they are not independently tracked transitive theorem provenance. The complete source replay is what reconstructs the dependency chain through the kernel. No standalone certificate verifier or general correctness theorem for the acceptance driver is claimed.

`locks/proof-inputs.json` seals source files for the accepted replay scope, both foundational source trees, generated OCaml parser/runtime files, upstream example object bytes, declared assumptions, expected statement terms, drivers, and byte inventories. Missing locks, conflicting digests, altered inputs, unexpected theorem names, missing theorem objects, changed statements and altered target bytes reject acceptance. Fresh GNU section extraction is compared with an independent PT_LOAD parser at each accepted top-level replay. The parser, extraction, hash implementation, container runtime, and acceptance orchestration remain trusted tools. The frozen local container archive enables offline restoration; its digest is checked by make setup.

No whole routine has all four required properties over the full input domain. In particular the event-range helpers establish modular containment of modeled data events, not physical permissions, canonical/nonwrapping accesses, executable instruction fetches or the full System V floating-point control-state frame. There are no checked non-vacuity witnesses yet. `make verify-clean` therefore returns nonzero even if every restricted checked subclaim replays. Controls 3 and 4 cannot be qualified before a genuine R1 positive composition package exists.

The allowance to execute OCaml includes powerful host-language operations outside the kernel, so source/runtime immutability is part of the trust policy. This project does not claim robustness against an attacker who may change the approved lock, driver, runtime and all proof sources together. Automated negative controls change individual inputs while retaining the original approved manifest and proofs.
